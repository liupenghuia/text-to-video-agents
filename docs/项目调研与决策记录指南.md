本文用于整理当前文生视频短剧系统中：

- 尚未明确的内容

## 2. 当前资料已经明确的部分

系统的核心链路已经比较清楚：

```text
用户输入
  ↓
Project
  ↓
Script Agent
  ↓
Storyboard Agent
  ↓
Scene / Shot
  ↓
Image / Keyframe
  ↓
Video Generation Job
  ↓
Shot Review
  ↓
Audio / Subtitle
  ↓
Timeline
  ↓
FFmpeg Render
  ↓
Final Asset
```

主要技术角色也已经形成初步分工：

| 角色 | 主要职责 |
|---|---|
| Agent | 理解需求、生成剧本、拆分镜头、生成 Prompt、参与质量判断 |
| Workflow | 编排阶段、控制状态迁移、决定下一步、处理失败和重试 |
| Worker | 执行 LLM、图片、视频、TTS、Vision、FFmpeg 等任务 |
| PostgreSQL | 保存业务事实和任务状态 |
| Redis / Queue | 临时调度、排队、并发和重试 |
| OSS / S3 | 保存图片、视频、音频、字幕和最终成片 |
| Provider | 提供 LLM、生图、生视频、TTS、Vision 能力 |

核心业务对象初步包括：

```text
Project
Episode
Scene
Shot
Asset
Job
Character
Timeline
Subtitle
```

## 3. 目前不明确或需要重新判断的内容

### 3.1 Project、Episode、Scene 的层级边界

流程文档主要围绕：

```text
Project → Scene → Shot
```

架构图又出现：

```text
Project → Episode → Scene → Shot
```

需要决定：

- 一个 Project 是否可以包含多个 Episode？
- Episode 表示短剧的一集，还是一次生成版本？
- 20 秒短视频是否也必须创建 Episode？
- Render 是针对 Project、Episode，还是一个渲染版本？

建议第一版统一为：

```text
Project
  └── Episode
        └── Scene
              └── Shot
```

即使一个项目只有一集，也保留 Episode 层，避免未来扩展时修改核心数据模型。

### 3.2 Director Agent 的职责过于宽泛

当前 Director Agent 可能同时负责：

- 理解用户需求
- 拆解任务
- 选择模型
- 修改 Prompt
- 判断质量
- 控制 Workflow

这容易造成 Agent 和 Workflow 的职责混乱。

建议明确：

```text
Agent：生成内容和做非确定性判断
Workflow：控制固定流程和状态迁移
Worker：执行具体任务
```

第一版可以让 Director Agent 负责用户需求理解和全局创作策略，不让它直接决定数据库写入、队列入队或 FFmpeg 启动。

### 3.3 continuous 不应简单等同于使用上一镜头最后一帧

当前流程中有如下假设：

```text
transition = continuous
→ 使用上一个 Shot 的最后一帧
```

这个规则不一定适用于所有视频 Provider：

- 不同模型对首帧、尾帧和参考图的支持不同
- 上一镜头的最后一帧可能模糊、畸变或构图不适合下一镜头
- 连续镜头可能更适合角色参考图和场景参考图
- 不同 Provider 的输入参数和限制不同

建议把输入策略显式建模为：

```text
NONE
FIRST_FRAME
LAST_FRAME
CHARACTER_REFERENCE
SCENE_REFERENCE
FIRST_AND_LAST_FRAME
```

由 `ShotGenerationContext` 决定实际传给 Provider 的输入。

### 3.4 Job 状态机还不完整

目前资料中的状态类似：

```text
PENDING
QUEUED
RUNNING
SUCCEEDED
FAILED
RETRYING
```

真实运行中还需要考虑：

```text
CANCELLED
TIMEOUT
PAUSED
WAITING_PROVIDER
DOWNLOAD_FAILED
REVIEWING
REVIEW_FAILED
RENDER_FAILED
```

需要定义：

- 谁可以修改 Job 状态？
- 哪些状态可以重试？
- 哪些状态是终态？
- Worker 崩溃后如何恢复？
- Provider 返回成功但下载失败时算什么状态？
- 用户取消项目后，队列中的任务如何处理？

### 3.5 阶段完成条件不够严格

不能只判断：

```text
all shots succeeded
```

还需要判断：

- 所有 Shot 是否已经归档为本地 Asset
- 所有 Shot 是否通过质量检查
- 是否仍有 Shot 正在重试
- 是否存在被跳过的 Shot
- 是否有用户锁定的素材版本
- 音频和字幕是否已经准备完成
- Timeline 是否已经生成并校验

建议使用明确的阶段门禁：

```text
VIDEO_ASSETS_READY
QUALITY_REVIEW_PASSED
AUDIO_READY
TIMELINE_READY
RENDER_READY
```

### 3.6 音频、对白、字幕的关系还不明确

目前流程是：

```text
TTS → 音频 → 字幕
```

但还需要确定：

- 台词从剧本、分镜还是独立 Dialogue 表读取？
- 每句台词是否属于某个 Shot？
- TTS 返回的音频如何对齐 Timeline？
- 旁白、对白、环境声如何区分？
- 没有台词时是否跳过 TTS？
- 背景音乐是否自动生成？
- 字幕时间来自 TTS、语音识别，还是 Agent 估算？

### 3.7 Provider URL 不能作为长期 Asset

第三方 Provider 返回的视频 URL 可能：

- 很快过期
- 只能访问一次
- 需要鉴权
- 下载速度不稳定
- 编码格式不统一

建议固定执行：

```text
Provider 结果
  ↓
立即下载
  ↓
校验媒体
  ↓
上传 OSS / S3
  ↓
Asset 标记为可用
```

业务数据库长期保存自己的 Asset URL 或对象键，不依赖 Provider 临时地址。

### 3.8 质量评估标准尚未可执行化

当前列出的质量指标包括：

- 人物一致性
- Prompt 对齐
- 视觉质量
- 连贯性

仍需明确：

- 分数如何计算？
- 阈值是多少？
- 哪些问题属于硬失败？
- 哪些问题只产生警告？
- Review 失败后是否自动重试？
- 重试时如何修改 Prompt？
- 最多重试几次？
- 哪些情况需要人工审核？

## 4. 必须调研和选择的内容

### 4.1 产品范围

需要确定：

- 第一版是单用户工具还是 SaaS
- 生成短视频还是连续短剧
- 是否支持多个 Episode
- 是否只支持 9:16
- 支持哪些视频时长
- 每个 Shot 的默认时长
- 是否允许用户编辑剧本和分镜
- 是否允许单独重新生成 Shot
- 是否保留多个生成版本
- 是否需要人工审核

### 4.2 AI Provider

需要调研和比较：

- LLM Provider
- 图片生成 Provider
- 视频生成 Provider
- TTS Provider
- Vision / Review Provider
- 首帧、尾帧、参考图支持
- Webhook 或 Polling 支持
- 平均生成耗时
- 失败率和限流规则
- 单次生成成本
- 商业使用限制
- 内容安全限制
- 返回文件有效期
- 是否允许保存、下载和二次处理结果

Provider 不应只按画质选择，还应区分：

```text
预览模型
正式模型
低成本模型
失败备用模型
```

### 4.3 Workflow 技术

候选方案包括：

- BullMQ + Redis
- Temporal
- Inngest
- Trigger.dev
- LangGraph
- 自研数据库状态机

第一版可优先评估：

```text
PostgreSQL 状态机 + BullMQ + Redis
```

理由：适合当前 Node.js Worker 架构，部署和理解成本较低，足以覆盖队列、重试、并发控制和基础恢复。

如果未来出现大量暂停、恢复、人工介入、补偿事务和复杂长流程，再评估 Temporal 等更强的工作流引擎。

### 4.4 数据库和数据版本

需要确定：

- 哪些数据使用关系表
- 哪些数据使用 JSONB
- Prompt 是否保存版本
- 每次生成是否保存输入快照
- Shot 重试是否创建新版本
- Asset 是否支持多个候选版本
- Timeline 是否可以回滚
- 项目删除和素材清理规则

必须保留生成时的上下文：

```text
使用了什么剧本
使用了什么 Prompt
使用了哪个模型
使用了哪些参考图
生成结果是什么
失败原因是什么
```

### 4.5 存储和媒体处理

需要选择：

- S3、OSS、COS 还是 MinIO
- 是否使用 CDN
- 公有 URL 还是签名 URL
- 视频最大尺寸和文件大小
- 统一的视频编码参数
- FPS、音频采样率和字幕格式
- FFmpeg 还是 Remotion
- 是否需要 GPU 渲染

### 4.6 前端方案

架构图写的是：

```text
Next.js + React + TypeScript
```

当前原项目则是：

```text
Vue 3 + Vite
```

需要明确：

- 继续使用 Vue，还是切换 React
- 是否新建独立前端
- 当前知识库是否继续保留
- 是否需要实时进度
- 是否需要拖拽式时间线
- 是否支持 Shot 单独编辑
- 是否支持视频版本对比

### 4.7 账户、权限与安全

需要确定：

- 登录方式
- 项目所有权
- 多用户协作方式
- 是否多租户
- Provider API Key 的保存方式
- Provider 调用是否全部经过后端
- 素材是否私有
- 下载链接是否使用签名 URL
- Webhook 是否验签
- 用户输入和生成结果是否需要审核
- 敏感内容如何拦截

### 4.8 成本和并发

需要估算：

```text
一次 20 秒视频需要多少 Shot
每个 Shot 平均生成几次
一个项目平均调用多少次模型
单项目平均成本
同时生成多个项目需要多少并发
失败重试的成本上限
```

必须设置：

- 用户级额度
- 项目级预算
- Provider 级限流
- Worker 并发数
- 单任务超时
- 自动重试上限
- 任务取消策略

## 5. 建议的调研优先级

### 第一优先级：确认系统能否跑通

1. 视频 Provider 是否支持所需的首帧、尾帧和参考图输入
2. Provider 结果是否可以稳定下载并长期保存
3. 真实生成耗时和失败率
4. FFmpeg 是否能稳定合成不同 Provider 的视频
5. Shot2 的连续性策略是否有效
6. Webhook 和 Polling 哪个更可靠

### 第二优先级：避免数据模型返工

1. Project / Episode / Scene / Shot 的层级边界
2. Shot 重试和版本模型
3. Asset 生命周期
4. Job 状态机
5. Timeline 数据结构
6. 音频和字幕的时间对齐方式

### 第三优先级：决定能否产品化

1. 用户和权限
2. 内容安全
3. 成本和额度
4. 并发和限流
5. 私有存储和下载权限
6. 监控、告警和备份

## 7. 各类记录应该怎么写

### 7.1 需求与范围表

用于记录“做什么、不做什么”。

建议字段：

| 字段 | 说明 |
|---|---|
| ID | 例如 REQ-001 |
| 需求 | 具体行为 |
| 优先级 | Must / Should / Later |
| 第一版是否实现 | 是 / 否 |
| 验收标准 | 如何证明完成 |
| 依赖 | 依赖哪些模块 |
| 状态 | Open / Accepted / Done |

示例：

```markdown
| REQ-001 | 用户可以单独重试 Shot | Must | 是 | 重试不影响其他 Shot | Job 幂等、Asset 版本 | Accepted |
```

### 7.2 调研记录

用于记录事实、来源和测试结果，不直接替代架构决策。

模板：

```markdown
# 调研主题

## 问题

需要选择什么？

## 候选方案

- 方案 A
- 方案 B
- 方案 C

## 调研范围

- 官方文档
- 官方价格
- API 示例
- 实际测试

## 关键事实

只记录可以验证的事实，不把推测写成事实。

## 对本项目的影响

会影响哪些模块、成本和风险？

## 暂定结论

当前推荐方案是什么？

## 待验证项

还缺什么真实测试？

## 调研日期

YYYY-MM-DD
```

Provider 调研应使用统一测试条件：

```text
相同 Prompt
相同参考图
相同 Shot 时长
相同分辨率
```

并记录：

```text
耗时
成本
成功率
人物一致性
画面质量
API 稳定性
下载行为
```

### 7.3 架构决策记录 ADR

用于记录会影响代码结构、数据结构或长期维护的选择。

模板：

```markdown
# ADR-001：标题

## 状态

Proposed

## 背景

为什么需要做这个选择？

## 候选方案

- 方案 A
- 方案 B
- 方案 C

## 决策

最终选择什么？

## 原因

选择它的事实和约束是什么？

## 放弃的方案

为什么暂时不选其他方案？

## 影响

会增加什么成本、限制或后续工作？

## 验证方式

如何验证这个决策是可行的？

## 日期

YYYY-MM-DD
```

状态建议使用：

```text
Proposed
Accepted
Superseded
Rejected
```

### 7.4 风险登记表

用于记录可能导致项目失败的问题。

建议字段：

| 风险 | 概率 | 影响 | 级别 | 缓解措施 | 验证方式 |
|---|---:|---:|---|---|---|
| Provider URL 过期 | 高 | 高 | Blocker | 生成后立即下载到 OSS | 模拟延迟下载 |
| Shot2 连续性差 | 高 | 高 | High | 支持多种参考输入策略 | 对比测试 |
| Webhook 重复回调 | 中 | 高 | High | provider_task_id 唯一约束 | 重放回调 |
| FFmpeg 编码不一致 | 中 | 中 | Medium | 统一转码参数 | 多 Provider 测试 |
| 自动质检误判 | 高 | 中 | Medium | 提供人工复核入口 | 构造失败样本 |

### 7.5 开放问题清单

用于记录尚未做出决定、但会影响实现的问题。

模板：

```markdown
## Q-001：是否支持人工修改 Shot Prompt？

状态：Open
影响：前端、数据库、重新生成流程
负责人：待定
截止日期：待定
决策条件：确认目标用户是否需要创作控制
```

## 9. 第一版建议结论

在没有更多调研结果前，建议采用以下默认方向：

```text
独立项目
Node.js + TypeScript API
Vue 或 React 二选一后固定
PostgreSQL
Redis + BullMQ
MinIO / S3 兼容存储
FFmpeg
Mock Provider + 可替换真实 Provider
```

第一版先完成一条可验证闭环：

```text
输入故事
  ↓
结构化剧本
  ↓
3～5 个 Shot
  ↓
静态 Keyframe
  ↓
Mock 或真实图生视频
  ↓
上传素材
  ↓
生成简单 Timeline
  ↓
FFmpeg 拼接
  ↓
输出 MP4
```

第一版暂不建议优先实现：

- 复杂 Director Agent
- 自动模型路由
- 多人协作
- 高级时间线编辑器
- 自动配乐 Agent
- 高级 Vision 质检
- 计费系统
- 大规模并发
- 多租户隔离

## 10. 总结

当前资料已经足够支撑一个可运行的文生视频短剧 MVP，但还不能直接视为生产系统技术规格。

项目继续推进时，应先完成：

1. 统一 Project、Episode、Scene、Shot 的数据边界。
2. 选择第一版 Provider 和视频输入策略。
3. 定义完整 Job 状态机和 Asset 版本规则。
4. 验证 Provider 下载、Webhook、重试和 FFmpeg 合成链路。
